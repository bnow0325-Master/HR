# HR 대표 개인 알림 배포 절차

## 적용 범위

HR의 확정 출퇴근/퇴근 취소, 승인된 휴가·출장을 내구성 outbox에 기록한다. 기존 비노우톡 직원채팅 inbound API를 재사용한다. 비노우톡 코드·배포, WorkBoard 코드·권한·데이터·배포는 변경하지 않는다. 직원 본인 확인은 본인의 기록만 포함하며 기존 수신 중단 정책을 유지한다.

매분 systemd 타이머가 HR 앱 내부 토큰으로 내부 API를 호출한다. 서버 시간대와 무관하게 요약 기준은 Asia/Seoul 09:00이며 월요일에는 월~일 주간 요약 한 건을 보낸다. 타이머 지연 시 해당 날짜의 실행을 보충하며 빈 당일 현황은 SKIPPED로 남긴다. 앱 응답 뒤의 즉시 발송이 중단되어도 outbox를 다음 실행에서 재시도한다. 채팅 저장 확인은 기기 푸시 수신 확인과 다르다.

## 승인과 실행 계정

대표의 개발·운영 배포 지시는 확인되었다. 별도로 서버 접근 정책과 파일 실행 승인을 지켜야 한다. 이미 거부된 Docker/보호 환경 경로를 변형 명령·다른 계정으로 조회하거나 새 sudo 정책·root 세션을 만들어 우회하지 않는다.

이 디렉터리의 `preflight.sh`와 `deploy.sh`는 **승인된 운영자가 root 권한으로 실행할 파일**이다. 파일이 존재하거나 로컬 검사에 통과했다는 사실은 서버 실행 승인·운영 배포 성공을 의미하지 않는다. 에이전트가 실행한다면 공식 Alpacon WorkSession과 검증 파일 실행 절차를 먼저 승인받는다. 일반 사용자로 실행하면 코드 77로 중단한다.

## 실행 전 확인

1. 최신 공식 `origin/main`과 기능 PR의 CI를 확인한다. 로컬 미커밋 변경을 보존한다.
2. 운영자가 정확한 파일 SHA-256을 확인한 `preflight.sh`를 실행한다. 출력의 실제 앱 이미지, Compose working_dir/project, HR DB health, HR webhook origin/path와 구성 여부를 기록한다. 출력에 암호·토큰·전체 환경파일은 포함하지 않는다.
3. 링크나 이전 문서만으로 운영 릴리스를 확정하지 않는다. 실제 컨테이너 작업 디렉터리와 이미지가 배포 인자와 일치해야 한다.
4. 기존 webhook이 `main.bnow.co.kr` 등 다른 곳이면 해당 경로의 실제 API/인증 계약을 운영자가 먼저 확인한다. 미확인 호스트를 임의로 허용하거나 토큰을 다른 곳으로 보내지 않는다. 현재 배포 스크립트는 공식 `chat.bnow.co.kr/api/staff-chat/webhooks/incoming`만 허용해 불일치 시 전환 전에 중단한다.
5. `git archive`로 최신 main 전체를 묶고 로컬·서버 SHA-256을 비교한다. 배포 전 태그를 공식 원격에 보존한다.

## 배포 파일 인자

```text
deploy.sh \
  /home/elonchoo/<latest-main>.tar.gz \
  <64자리-archive-sha256> \
  <40자리-main-commit> \
  sha256:<실측-기존-image-id> \
  <실측-기존-compose-working-directory> \
  <앞7자리commit>-YYYYMMDD-HHMM-hr-notifications
```

스크립트는 다음을 순서대로 수행한다.

- 현재 앱/DB와 검토한 인자가 일치하는지 검증한다.
- 새 릴리스와 root 전용 백업 경로를 만든다. 기존 원본을 덮어쓰지 않는다.
- HR 환경파일을 값 출력 없이 새 릴리스로 복사하고 scheduler 토큰만 새로 생성한다.
- 이전 소스/환경, 이전 이미지 참조, HR 전용 MariaDB 전체 덤프와 해시, 즉시 실행할 코드 복원 파일을 보존한다.
- 새 임시 DB로 덤프를 복원하고 outbox SQL을 적용하여 다섯 핵심 테이블을 확인한다. 생성한 임시 DB만 정리한다. 이는 HR 전용 배포 검증이며 회사 공유 DB 전체 복원의 증거가 아니다.
- 최신 main 전체로 app/migrate 이미지를 빌드하고 새 마이그레이션을 적용한다. 앱 전환 실패 시 이전 이미지/소스로 복원하며 신규 출퇴근·outbox를 과거 DB로 되돌리지 않는다.
- 앱 health/실제 작업 디렉터리/공개 주요 경로를 확인한 뒤 타이머를 설치한다.

첫 실행 이전에 타이머가 존재하면 자동 덮어쓰기 대신 중단한다. 재배포는 현재 운영 버전을 대조해 별도로 검토한다. 기존의 보호된 백업 경로를 조사하기 위한 스크립트가 아니다.

## 운영 수용 확인

- 대표 HR 세션에서 `/admin/notifications`의 연결 확인 버튼을 누른다. 실제 출퇴근 기록을 만들지 않는 고정 진단 문구이다.
- 응답의 SENT/remoteRoomId/remoteMessageSeq를 대표+시스템 두 명만 참여하는 기존 direct 방과 비교하고 실제 비노우톡 화면에서 한 건만 보이는지 확인한다. 같은 날 두 번째 클릭은 같은 메시지를 재사용해야 한다.
- 익명·일반 직원·다른 관리자·비활성 계정은 진단 API/화면에 접근할 수 없어야 한다. 대표 이메일이 같더라도 HR ADMIN이 아니면 차단한다.
- 실제 직원 출퇴근·승인 원장을 테스트 목적으로 만들지 않는다. 합성 흐름은 격리된 CI DB에서 검증한다. 다음 실제 업무 이벤트는 담당자의 정상 등록 후 기록과 수신을 대조한다.
- Android/iPhone의 단말 푸시·앱 배지·실제 설치 상태는 채팅 저장과 별도로 확인한다. 미검증 항목은 완료로 표시하지 않는다.

## 복원

배포 출력의 root 전용 백업 디렉터리 안 `rollback.sh`를 승인된 운영자가 실행한다. 스케줄을 중지하고 직전 앱 이미지와 Compose 경로를 복원한다. HR 원장·outbox와 이후 데이터는 보존한다. 백업 DB로의 운영 덮어쓰기는 이 복원 절차에 포함하지 않는다.

## 검사

`npm run test:notifications`는 규칙 테스트, 실제 route/module를 사용한 가짜 인증/DB 경계 테스트, scheduler 통신 실패 테스트를 실행한다. CI 전용 `hr_ci@localhost/bnow_hr`에서만 실제 MariaDB 잠금/트랜잭션 테스트 두 건이 실행되며 다른 환경에서는 명시적으로 건너뛴다. `npm run check`, CI 결과, 실제 화면 및 운영 수신 검증을 각각 기록한다.
